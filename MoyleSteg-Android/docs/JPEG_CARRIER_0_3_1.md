# JPG 载体 → PNG 成品 · Android 0.3.1-alpha

在隐藏页选择 JPG／JPEG 照片和秘密文件，检查实际容量，输入口令或选择密钥，处理后保存 `.png` 成品。
成品使用已有 PNG v1 协议，可由兼容的 Windows 和 Android 版本恢复。Windows 1.5.1 已有这一能力。
原始照片不被写入或替换；JPG 转成 PNG 后，文件体积可能明显增加。

## 图像处理与预算

- 按签名判断 JPEG，不依赖 `.jpg`／`.jpeg` 文件名或文档提供方 MIME。
- 选择阶段仅扫描有界头部，显示可取得的照片显示尺寸。信息不足时不猜尺寸；任务对实际捕获的字节重新检查。
- 解码前检查编码字节预算、像素预算、工作内存与当前可用堆。预算包含平台 Bitmap 和最终 RGBA 像素。
- EXIF 的旋转和镜像在嵌入之前应用；不在隐写完成之后再旋转或压缩。输出没有 EXIF／GPS 等原照片元数据。
- 像素直接交给现有 Kotlin PNG 隐写流程，避免额外生成一张中间 PNG 再解码。
- 容量预检使用实际压缩结果。需要时按比例扩容，仍受像素与内存限制；不会悄悄降低照片采样尺寸。
- 保存私有临时 PNG 后，重新读取并认证、比较载荷与原文件名，通过后才允许导出。

本功能处理 JPEG 主图；不保留相机附加影像、HDR 增益图或照片元数据。
平台 JPEG 解码器可能容忍部分受损数据；应用的结构、长度和预算检查不是完整 JPEG 格式审计。
此行为仅适用于创建载体。**恢复和只读验证继续使用捕获的原始 PNG／GIF／SAES 字节，不经过平台 Bitmap 转换。**
比如一个真实 PNG 被聊天软件保存为 `.jpg`，仍按 PNG 内容识别，避免损失透明像素中的 RGB 隐写位。

## 微信与 QQ 保存观察

用户在本轮报告：应用直接保存到相册时尺寸正常；经微信二次保存后显示 0×0，但隐藏内容仍能恢复；
经 QQ 勾选原图发送和再次保存，尺寸与恢复均正常。这里记录的是用户测试，维护方未在这些聊天应用与手机上独立复测。

该对照把异常范围缩小到微信二次保存／相册索引环节，但不能只凭相册截图确定是哪一字段或哪一组件导致。
0×0 不等于文件内部像素尺寸为零，也不表示加密已失效。可在应用中查看按文件头识别的尺寸，并执行只读验证。
不要为了修正相册显示而裁剪、缩放或重新编码已有隐写图。

这些测试也不保证聊天软件的所有版本、图片大小和发送方式都会保留字节。
发送时保留原文件，接收后验证；要确认完整容器未发生任何字节变化，可比较发送前后的完整容器 SHA-256。
原文件 SHA-256 则用于核对恢复内容，二者用途不同。
