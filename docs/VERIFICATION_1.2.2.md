# 1.2.2 只读验证修复与验证说明

1.2.2 修复只读验证中“已认证的容器”和“报告的整容器 SHA-256”可能来自不同内容的问题。容器格式 v1、密钥格式 v1 及既有加密协议保持不变。本文仅使用合成数据描述缺陷与验证范围；本机路径、原始诊断 JSON、截图及私人调查记录不进入公开工程包。

## 缺陷与修复边界

旧实现先从输入路径读取并认证 PNG 或 SAES，再重新打开原路径计算整容器 SHA-256。合成复现在认证完成后、哈希阶段开始时原地覆盖输入，并保持文件大小及修改时间不变，可以使成功结果同时包含容器 A 的认证结果和容器 B 的整容器摘要。两次读取分别成功，不能证明它们针对同一组字节。

本轮核对 Git 历史，1.2.0 与 1.2.1 的 `_verify` 函数 AST 完全相同；这是旧验证流程的关联缺陷。最初针对 1.2.1 执行的 12 个合成用例中，保持修改时间的 4 个用例失败，普通状态变化和静止输入的 8 个控制用例通过。

1.2.2 在共享验证服务中先创建私有的加密容器临时副本，再以同一副本完成认证和整容器 SHA-256。复制按块进行，写入副本的上限固定为打开输入时取得的初始长度；至多额外读取一个字节以检查增长，持续增长的输入不会使复制无限追赶新增内容。既有载荷大小、图像像素预算和取消检查继续适用，可观察的输入状态变化仍会导致拒绝。临时副本需要容器大小对应的额外磁盘空间，包含加密容器，不写出恢复后的明文文件；成功、失败和取消均清理临时副本。

复制时还记录所捕获字节的 SHA-256，认证后对副本计算的摘要必须与之相等；副本自身在认证后被改写，即使恢复时间戳，也会被拒绝。PNG 的完整文件大小不被错误地当成载荷大小，合法附加字节仍计入完整容器摘要。复制前已知的像素超限、SAES 头部长度超限和无效资源参数均提前拒绝。

成功结果中的认证状态及整容器 SHA-256 因而描述同一个验证副本。原路径在复制完成后被替换或覆盖，不会使哈希阶段重新读取另一份容器；结果不承诺原路径此时仍保存相同内容。复制过程不是严格的操作系统文件快照，也不能证明所有复制期间的恶意并发修改都可被发现。

整容器 SHA-256 用于标识此次验证的容器字节；它不提供数字签名或发布者身份认证，也不替代容器自身的认证检查。PNG 解码和载荷处理仍使用内存，分块复制并未引入流式大文件加密格式或新的峰值内存保证。默认预算仍为 **25,000,000 像素、256 MiB 原始文件**。

## 发布内容与重跑入口

使用 `scripts/run_tests.py` 或 `运行测试.bat` 运行项目支持的测试入口；核心测试与原生 Windows 界面选项见 `README_DESKTOP.md`。构建后必须运行实际 EXE 的 `--self-test`，将诊断报告写在便携运行目录之外。完整公开打包及摘要核验命令见 `RELEASE.md`。

本文件以精确文件名加入源码发布白名单，并复制到便携运行目录；打包同时要求两处存在。便携运行库仍必须与干净构建的 `RUNTIME_MANIFEST.json` 成员、大小和 SHA-256 完全一致，复制入 ZIP 时再次核验。新增、缺失、修改的运行库文件及未批准的文档仍会被拒绝。最终公开 ZIP 用 `RELEASE_MANIFEST.json` 核对全部实际成员与摘要。

`RELIABILITY_1.2.1.md` 与 `SECURITY_FIXES_1.2.md` 保留旧版本历史结果；`SHA256SUMS.txt` 只记录最初导入的 v1.0 基线。它们均不替代本版本验证。

## 实现依据与限制

- [Python TemporaryDirectory](https://docs.python.org/3/library/tempfile.html#tempfile.TemporaryDirectory) 用于上下文退出清理。正常成功、异常与协作取消路径已测试；强制结束进程、断电或清理权限故障不在自动清理保证内。
- [Pillow 文件处理文档](https://pillow.readthedocs.io/en/stable/reference/open_files.html)及 [Pillow 12.3.0 ImageFile 实现](https://github.com/python-pillow/Pillow/blob/12.3.0/src/PIL/ImageFile.py)用于核对已打开句柄的读取和关闭语义。
- 本修复保证结果与受控副本关联，不提供操作系统快照，也未进行正式密码学审计。临时空间和现有解码内存预算仍需满足。
